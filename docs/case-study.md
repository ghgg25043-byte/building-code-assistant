# 产品案例：建筑场景检索与人工研读工作流

这是一个从 0 到 1 的产品原型，用来验证一个问题：建筑设计人员在查找要求时，是否需要一套同时呈现**候选线索、资料缺口和人工研读记录**的工作流。当前公开版使用 14 个[原创虚构条目](../data/demo-source.md)展示交互，不提供真实规范依据或工程结论。

## 用户任务与待验证假设

设想的首批用户是需要在方案或施工图阶段查找资料的建筑设计人员。一个典型任务是：“我需要确认办公楼公共走廊的问题涉及哪些资料，哪些项目条件尚未明确，并把核对过程交给负责人。”这来自产品假设，**尚未经过真实用户访谈证实**。

| 假设 | 为什么重要 | 下一步如何验证 |
| --- | --- | --- |
| 用户花在确认资料版本、位置和适用条件上的时间，可能超过找到关键词的时间 | 决定产品应优化完整核验任务，而非只追求搜索速度 | 访谈 5–8 名从业者，复盘最近一次实际查找任务并计时 |
| 混合问题容易让候选条目看起来“覆盖了全部提问” | 误导性的完整答案可能比明确拒答更危险 | 让受访者完成走廊与消防混合任务，观察是否注意到缺口 |
| 研读理由与交接状态需要跟候选放在同一处 | 决定工作簿是否值得保留 | 比较使用原有工作方式与本原型后的交接遗漏、总耗时 |

## 产品决策

1. **只给候选，不给合规结论。**系统展示 D 编号、命中原因和场景记录项；真实项目仍要由有权使用正式资料的专业人员核验。
2. **把资料缺口做成结果状态。**候选定位、部分覆盖、资料不足是三个不同状态。混合问题中，未覆盖专题不会被另一个候选“顺带回答”。
3. **保留人工判断的出处。**本地应用允许记录纳入理由、待核对条件与交接状态，并导出 Markdown 工作簿。系统不会把人工备注误标成条目已专业复核。
4. **用虚构资料公开演示。**[在线体验](https://ghgg25043-byte.github.io/building-code-assistant/)在浏览器内检索原创练习条目；真实规范资料接入必须先解决使用许可、版本和专业审核。
5. **AI 是可选的受限辅助。**本地应用的模型接口默认关闭，单次主动勾选后仅允许输出固定格式的候选 D 编号提示；它不能补写规范要求、数值或结论。在线演示不调用模型。

## 从问题到记录

| 阶段 | 用户做什么 | 系统做什么 | 保留的边界 |
| --- | --- | --- | --- |
| 提问 | 写下场景、用途和已知条件 | 对虚构资料进行主题匹配 | 城市等条件只记录，不伪装成适用性判断 |
| 看候选 | 阅读 D 编号、命中原因、原创资料入口 | 显示候选或资料缺口 | 条目不对应真实规范 |
| 人工研读 | 标记待核对项、填写理由 | 在浏览器工作簿中保存记录 | 人工备注不等于专业认证 |
| 交接 | 导出 Markdown 并交给负责人 | 提供可复查的问题与备注 | 无自动工程结论 |

例如输入“办公楼公共走廊净宽和消防疏散距离有哪些要求？”，在线演示会返回虚构 D-11，同时把真实消防专题标为未覆盖。单独询问消防疏散距离时返回零候选，不编造条号或数值。

## 当前证据与限制

已完成本地接口与检索、虚构资料治理、三状态提示、浏览器工作簿、Markdown 导出和在线虚构演示。33 项 Python 单元测试、12 个开发者回归样本及前端冒烟测试用于验证软件行为；这些数字**不是**建筑专业准确率、用户满意度或节省时间的证据。没有真实用户访谈、专业标注或商业试点数据。

下一轮将先进行 5–8 场任务访谈，整理用户现有检索渠道、版本核验方式、交接形式和错误成本。若获得真实资料使用权限，再在受控环境建立独立标注题集，比较“从提问到专业人员完成核验记录”的总耗时、引用位置正确率、资料缺口识别率和误导性肯定次数。公开演示语料仍保持虚构，直到许可与专业审核条件都满足。
